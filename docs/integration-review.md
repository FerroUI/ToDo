# Microsoft To Do integration review

Reviewed **2026-11-22** against the primary Microsoft documentation linked below and the repository implementation. The remaining-differences round starts from `13dbc908`; the earlier service review started from `fb15bde12c68ca48cc3dad01cafde6019628cacf`. This review covers external services and data portability; it does not certify complete product or visual parity.

## Findings and changes

The earlier round added deployment configuration, browser MSAL, automatic Graph/delta sync, remote attachment transfer, Planner assignments, and portable/Graph archives to the local-first Rust app. The remaining-differences baseline still lacked native Microsoft services, a category palette, national-cloud routing, real PST tools, and synchronization of local presentation settings.

This round adds a native service worker with MSAL Node and file services, read-only Outlook categories with incremental consent, fixed global/GCC High/DoD routing, an owner-run registration helper, bounded Outlook PST import/export, and opt-in OneDrive synchronization of the app's My Day/groups/order/appearance. Optional-service cancellation and failures preserve base task authorization. Restore still creates an independent local copy and pauses/disconnects every connector. [Setup and operation](MICROSOFT.md) documents exact behavior and limits.

The deployment still needs an owner-controlled Entra registration and public client ID. The helper can prepare/apply public configuration through the owner's existing Azure CLI session; it has not been run against a real directory. No registration was invented, no client secret is embedded, and no authenticated Microsoft account was used for live acceptance testing during this implementation.

## Architecture and data integrity

The Rust document and MVVM state remain authoritative. Shared service modules live under `crates/todo-browser/wwwroot/cloud/`; archive validation and file staging live under `wwwroot/backup/`. The native Rust UI runs those same modules in a private Node worker with native authentication, file storage, and pipe transport adapters. PST parsing lives in the reusable `todo-interop` crate, with a dedicated browser WASM bridge. Provider identities and synchronization history are separate from task fields. Planner projections carry explicit external provenance, and domain actions guard unsupported operations.

One host queue serializes Microsoft work. Account changes and restore/export pause scheduled work; Web Locks coordinate browser tabs, while a native application-directory lock prevents competing processes. UI-thread snapshot comparison guards native worker document replacement. To Do uses three-way merging and conditional updates. Planner uses independent task/detail revisions and recoverable checklist writes. The complete sync spans multiple requests, so it cannot be atomic. A changed source discovered during a move leaves both task copies available for review.

Files travel with moves: download source content, record checksums, populate the destination, then recheck the source before deletion. Recovery metadata distinguishes previously uploaded content from local additions. Account-specific cache keys and document bindings prevent another account from inheriting pending writes.

Scheduling limits idle work, backs off transient failures, stops on base authentication/conflicts, and permits Planner, categories, and OneDrive settings to pause independently. An optional-consent redirect cancellation can restore only the explicitly selected previous account using a bounded one-shot marker tied to the exact client/tenant/cloud/redirect; it cannot resurrect a disconnected session. Delta snapshots are committed only after complete reads. These are implementation decisions, not guarantees about network latency or Microsoft's availability.

### Presentation synchronization

OneDrive synchronization is opt-in and uses only the app-folder delegated scope. The same app registration/account/cloud must be used on every participating installation. First enable adopts existing remote field values; subsequent edits use field-level Lamport revisions with deterministic device ordering. Each device owns a replica file, avoiding an assumption of transactional updates to one shared file. Local identities and pending uploads are journaled; a late local edit or uncertain network result is reconciled before accepting a replacement.

The versioned schema admits a defined set of My Day, group, ordering, appearance, and workflow fields. Credentials, task content, files, and connector opt-ins are excluded. Reads are capped at 4 MiB and 50,000 fields per replica, 128 replicas, and 16 MiB aggregate. Remote metadata, full-response length, revision, schema, and selected-cloud download hosts are validated before cache publication. Preauthenticated downloads send no Graph token/credentials/referrer and refuse redirects/partial responses. Old replicas are not pruned automatically; users retain control of the OneDrive folder. This extends this app across devices without claiming Microsoft's private presentation protocol or immutable backup semantics.

### Portable restoration

| Archive kind/version | Payload | Restore behavior |
| --- | --- | --- |
| `ferroui.todo.backup` / 1 | Canonical local document, unique file bytes, metadata, opaque file keys, SHA-256. | Validate all content, allocate fresh file keys, replace the local document once. |
| `ferroui.microsoft-todo` / 1 | Fresh Graph lists/tasks, original returned properties, hydrated children, files with source mappings/checksums, export time. | Allocate new local identities, retain original task data for restricted future-upload seeding, then use the portable restore pipeline. |
| Outlook PST | ANSI 14/15 or Unicode 23 input; new Unicode 23 task-store output with standard properties/files and versioned app metadata. | Isolated bounded parsing, preserve original typed MAPI fields, then use the same independent-copy portable restore pipeline. |

The account archive performs no remote writes. It covers accessible To Do data, excluding Planner plans/mailboxes, and is not a server-transactional snapshot. Archive limits are 25 MiB per file, 128 MiB of decoded files, 32 MiB metadata/document JSON, and 256 MiB input/output. PST additionally caps item/folder counts and traversal depth; [its guide](OUTLOOK-PST.md) documents mappings, worker budgets, unsupported attachment kinds, RTF/native recurrence retention, and export loss accounting.

Restore validates version, IDs, relationships, file references, sizes, base64, and checksums before storage writes. Fresh keys protect existing attachments. Guards detect concurrent local edits; failure rolls back newly staged blobs. Unsupported future versions are rejected.

Successful restoration disables auto-sync, Planner, Outlook categories, OneDrive settings, and native keep-running; removes active cloud/provider bindings and assignment/flagged-email markers; disconnects the local Microsoft session; and clears mappings. Source URLs survive. Restored tasks are independent local copies requiring intentional connection/sync before publication. Tokens, profile wrappers, and synchronization sidecars are not archive payloads.

## Service lifecycle context

As reviewed on 2026-11-22, Microsoft says its To Do applications will retire **June 30, 2027**. It distinguishes the underlying service, APIs, and synchronization, whose later retirement dates are not yet announced. Export guidance is promised before app retirement, but format details and limits are not published. Existing tasks will not automatically migrate to Planner, and Planner is unavailable to personal Microsoft accounts. These facts affect planning; they do not establish that Graph has already retired. [Microsoft's transition guidance](https://support.microsoft.com/en-us/planner/to-do-to-planner).

## Provider capabilities across input paths

Planner task restrictions apply to native menus, detail actions, swipe rails, mouse and held-touch drag, keyboard deletion, and bulk operations. Planner swipes expose My Day only; flagged-email tasks cannot move into a personal list. Single-action rails use their actual width for drag limits and settling thresholds. Rejected protected operations preserve the current selection and cannot produce a false deletion-success message. These policies remain enforced by the Rust domain beneath every UI route.

The combined-input browser review also exposed a framework lifetime bug: an already completed fallback drag could consume the next mouse press before its async cleanup ran. The FerroUI submodule includes a synchronous completed-result guard, with focused regressions for drop and Escape completion before future cleanup. App-level gesture ownership and cancellation policies remain in the existing coordinator.

## Verification and limits

The JavaScript suite exercises production modules with controlled MSAL, storage, timers, Graph, and native worker fixtures. Focused tests cover registration payloads, cloud/scope isolation, optional-consent cancellation, category refresh races, OneDrive schema/merges/pending-write recovery, token-free downloads, redirects, scheduling, deltas, file/move recovery, Planner revisions, archive checksums, and document replacement guards. PST tests generate actual Unicode stores and parse their task/file/named-property content with Microsoft's reader. Rust tests cover model constraints, connected-service state, document validation, and PST projection.

Run `node --test scripts/*.test.mjs` and the repository's current Rust/browser CI commands. Fixture tests establish implementation behavior, not a real registration, tenant policy, account license, live cross-device round-trip, OS notification/tray result, or desktop Outlook import. Final CI/deployment results and authenticated account acceptance must be recorded separately. [Native](NATIVE-MICROSOFT.md) and [PST](OUTLOOK-PST.md) guides record their platform and format-specific limits.
